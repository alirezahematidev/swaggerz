    04Reference

    Diagnostics

    Every diagnostic code, what it means and, for many, an example the compiler ran with the fix.

    Every problem is reported as a diagnostic with a stable code, a severity, a message, and when available a location (file, JSON pointer, line and column), the operation it relates to and a hint. Codes are stable across patch releases; --json output includes them for tooling.

    • error — generation stops and nothing is written.
    • warning — output is generated; something was ignored, interpreted or may not match the specification exactly.
    • info (notes) — shown with --verbose.

    The CLI exits with 2 when an error is a configuration problem (config/*) and with 1 for other errors. Terminal output shows control characters from the specification or plugins as \xNN escapes; --json output contains the text unchanged (JSON-escaped).

    overlay/invalid-targeterror

    Mocks

    mock/invalid-examplewarning

    Example: An example its own schema rejects

    mock/unsatisfiablewarning

    features.mocks: no generated value satisfies the schema (a model that requires itself, contradictory constraints, never); the fixture may not validate

    Example: A model that requires itself

    Lint findings

    lint/operation-idwarning

    An operation has no operationId: its function name is derived from the method and path and changes with them

    Example: An operation without an operationId

    Fix. Add an operationId, so the function keeps its name when the path changes.

    lint/operation-id-styleinfo

    An operationId is not an identifier in the naming.operations style: the exported function has another name

    lint/operation-tagsinfo

    An operation has no tags: it is generated into the default group

    lint/undeclared-taginfo

    A tag used by operations is not declared in the top-level tags

    lint/operation-summaryinfo

    An operation has neither a summary nor a description for its JSDoc

    lint/success-responsewarning

    An operation documents no 2xx or default response: it resolves with void

    lint/response-schemawarning

    A JSON success response has no schema: the operation resolves with unknown

    Example: A JSON response without a schema

    Fix. Describe the body with a schema; until then the function resolves with unknown.

    lint/inline-schemainfo

    A JSON request or response body is an inline object schema, named after the operation and not reusable

    Example: An inline request body

    Fix. Move the schema to components.schemas and reference it, so other operations can share the type.

    lint/untyped-schemainfo

    A named schema has no type, properties or composition: it is generated as unknown

    lint/duplicate-schemainfo

    Named schemas are structurally identical: the client contains duplicate types

    lint/unused-modelinfo

    A named schema is not used by any operation (still generated unless output.models: 'used')

    lint/missing-serversinfo

    No server is declared and client.baseUrl is not set: the client has no default base URL

    Example: No server and no base URL

    Fix. Declare servers, set client.baseUrl, or call client.setConfig({ baseUrl }) at startup.
